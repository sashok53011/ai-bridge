# Контекст проекта

Этот файл — перенос знаний из старого проекта (`Login-Template`) в новый.
Читается целиком перед началом работы.

## 1. Зачем продукт

**AI-приставка**: приложение-посредник между другими приложениями и
AI-провайдерами. Пользователь держит каталог провайдеров (OpenAI, Anthropic,
Ollama, LM Studio, …), включает нужные, хранит свои API-ключи **на устройстве**
и проверяет, работает ли провайдер и какая модель у него есть.

Долгосрочная цель — чтобы другие приложения подключались к приставке и
пользовались её выбором провайдера. Поэтому форма «локальный HTTP-сервис»
(OpenAI-совместимый) важнее, чем форма «приложение с интерфейсом».

## 2. Из чего состоит система

| Часть | Технология | Где живёт |
|---|---|---|
| Сервер каталога | PocketBase (бинарник + JS-хуки) | **свой инстанс** `pb.devhorizon.online` (FreedomBox, `127.0.0.1:8091`); до 16.10.2026 — общий `app.devhorizon.online` |
| Старый клиент | Flutter (Dart) | Android-приложение — **не трогаем** |
| Старая веб-панель | HTML/JS/CSS | `https://app.devhorizon.online/ai-providers/` |
| **Новое приложение** | **Python** | **Эта папка — начало с нуля** |

Сервер **общий**: новое приложение ходит в тот же каталог и ту же статистику,
что и старое. Поэтому суперпользо­ватель видит свежие данные о популярности
и доступности от всех клиентов сразу.

## 3. Сервер PocketBase

Адрес: `https://pb.devhorizon.online` — **свой инстанс** на FreedomBox
(`127.0.0.1:8091`, служба `pocketbase-ai`, данные
`/home/sashok5301/pocketbase-ai/pb_data`, суперпользо­ватель — новый
аккаунт). До 16.10.2026 приставка ходила в общий каталог старого
проекта (`app.devhorizon.online`); тот инстанс остался прежнему
проекту и не трогается.

SQL Playground в веб-интерфейсе доступен всем вошедшим. Читает
SQLite напрямую при настройке `AI_BRIDGE_SQLITE_PATH` на `data.db`.
Это локальный файл, а не SQL endpoint PocketBase. Админ выполняет
любой SQL (SELECT/INSERT/UPDATE/DELETE/PRAGMA), обычный пользователь —
только SELECT. Провайдеры и модели синхронизируются из каталога в
отдельный `catalogue.db` и тоже видны в SQL Playground. Для включения
нужен `AI_BRIDGE_SQLITE_PATH` и ACL-права на чтение базы и запись
в `AI_BRIDGE_HOME`. Без настройки раздел объясняет, что требуется
для запуска.

Марруты (реализованы в `deploy/pb_hooks/` старого проекта):

```
GET    /api/ai-config        -> { version, updated, canEdit, providers }
PUT    /api/ai-config        -> суперпользо­ватель: заменяет каталог;
                                обычный пользователь: сохраняет только переключатели
DELETE /api/ai-config        -> обычный пользователь: чистит свои переключатели
GET    /api/ai-config/meta   -> диагностика

GET    /api/ai-stats         -> статистика по всем провайдерам
POST   /api/ai-stats         -> отчёт о проверке: { providerId, model, ok, error }

GET    /api/ai-trash         -> корзина (только суперпользо­ватель)
POST   /api/ai-trash/restore -> вернуть из корзины
DELETE /api/ai-trash/{id}    -> очистить одну запись
DELETE /api/ai-trash         -> очистить корзину
```

Вход — под коллекцией `users` (`/api/collections/users/auth-with-password`),
ответ содержит `token`, который передаётся в заголовке `Authorization`
**без префикса Bearer**. Суперпользо­ватель входит через коллекцию
`_superusers` — тогда `canEdit = true`. Клиент пробует обе коллекции:
400 на `users` у админского аккаунта — это не опечатка, а место входа.

**PUT `/api/ai-config` у суперпользо­вателя заменяет каталог** (записи без
имени отбрасываются, отсутствующие уходят в корзину), поэтому флаги
«включён» ему отправлять нельзя — у админа сервер их и не хранит
(`viewFor({}, true, "")` всегда возвращает `enabled: false`). Переключатели
суперпользо­вателя — только на устройстве. Обычному пользователю PUT
принимает полные записи видимого списка: неотправленное стирается
(`writeFlags` заменяет файл), а незнакомые записи становятся его
предложениями.

## 4. Формат каталога

```json
{
  "version": 3,
  "updated": "2026-10-13T14:26:38.208Z",
  "canEdit": false,
  "providers": [
    {
      "id": "ollama",
      "name": "Ollama",
      "url": "http://localhost:11434/v1",
      "model": "llama3.2",
      "fallbackPriority": 10,
      "loginUrl": "",
      "getApiKeyUrl": "",
      "logoUrl": "",
      "logoAsset": "ollama",
      "status": "active",
      "origin": "admin",
      "authorId": "",
      "authorName": ""
    }
  ]
}
```

`id` — постоянный, по нему всё сходится; восстановление из корзины возвращает
запись **под тем же id**, и у людей подхватывается сохранённый ключ.

## 5. Статусы и правила синхронизации

| Статус | Поведение |
|---|---|
| `active` | обычная запись |
| `dead` | админ пометил как неработающую: **пользоваться можно**, но проверять нельзя, и она скрыта у тех, кто её не включал |
| `disabled_for_all` | выключена для всех: исчезает у всех; у включивших её раньше остаётся с пометкой и кнопкой «выключить» |

Правила, которые уже приняты и проверены:

- **Включённые человеком записи не удаляются никогда** — даже если каталог их
  больше не отдаёт. Человек включил сам — выключает сам.
- Выключенные берутся из каталога; помеченные `dead`/`disabled_for_all` в
  список не попадают.
- Удаление из каталога отправляет запись в корзину (восстановимо), но не
  трогает тех, кто включил.
- Предложения (`origin: "user"`) видит только автор и суперпользо­ватель;
  суперпользо­ватель публикует их на всех.

## 6. Статистика

Смысл показателя — **сколько человек смогли пользоваться**, а не сколько раз
проверяли. Формат хранения (по каждому провайдеру и модели):

```json
{
  "ollama": {
    "version": 1,
    "providerId": "ollama",
    "updated": "2026-10-13T14:26:38Z",
    "models": {
      "llama3.2": {
        "ok": 5, "fail": 2,
        "usersOk": 5, "usersFail": 2,
        "last": "2026-10-12T21:00:00Z",
        "lastStatus": "ok",
        "lastError": ""
      }
    }
  }
}
```

Человеку показывается как `5 (2) · 12.10 21:15` — успешно, с ошибками
(в скобках) и время последнего отчёта. Без отчётов — пустое место, ноль
показывать не нужно.

## 7. Безопасность — главное правило

**API-ключи никогда не покидают устройство.** Не на сервер, не в логи.
Серверу достаточно знать, что проверка прошла успешно (это и есть статистика).
Ключ живёт в хранилище приложения (на Android — защищённое хранилище,
в браузере — localStorage, в новом приложении — файл в домашней папке).

Операции, доступные только суперпользо­вателю: изменение каталога, публикация
предложений, корзина.

## 8. Провайдеры: два разных адреса

У провайдера **два корня**:

- список моделей — OpenAI-совместимый путь `<адрес каталога>/models`
  (обычно это `.../v1/models`);
- нативный API Ollama — в корне сервера: `POST /api/pull` (загрузка модели),
  `GET /api/tags`.

Пример: каталог даёт `http://localhost:11434/v1`, значит список моделей —
`http://localhost:11434/v1/models`, а загрузка — `http://localhost:11434/api/pull`.

Ответы на список моделей бывают двух видов:
`{"data": [{"id": "..."}]}` (OpenAI-совместимые) и `{"models": [{"name": "..."}]}` (Ollama).

## 9. Известные грабли

- **Ollama и браузер.** Запросы с веб-страницы блокируются, пока не прописано
  `OLLAMA_ORIGINS=https://app.devhorizon.online` (и перезапущен Ollama).
  Из приложений этой проблемы нет.
- **Адрес с телефона.** `localhost` на телефоне — это сам телефон. Для доступа
  к Ollama на ПК нужен его адрес в локальной сети (`http://192.168.0.x:11434/v1`);
  из эмулятора Android — `10.0.2.2`.
- **Ключ без заголовка.** Если ключа нет, заголовок `Authorization` не шлём
  вовсе: пустой `Bearer ` путает часть провайдеров.
- **401 без ключа — это не поломка**, а просьба ввести ключ. Поломка — это
  401 при уже введённом ключе.
- **Консоль Windows** по умолчанию cp1251: для русского текста нужно
  `sys.stdout.reconfigure(encoding="utf-8")`.
- **Суперпользо­вель и коллекция `_superusers`.** Вход админского аккаунта
  через `users` даёт HTTP 400 «Failed to authenticate» — это не поломка.
  Клиент пробует `users`, потом `_superusers`, и в ошибке оставляет обе
  причины.
- **Сообщение сервера важнее статуса.** PocketBase в отказах присылает
  `{"message": "..."}`; голый «HTTP 400» без него диагностику убивает.
- **Установка на Debian: CRLF.** `git archive` на Windows отдаёт файлы
  с `\r\n`, а bash на Debian читает «pipefail\r» как неизвестную опцию.
  Установщик сам себя перезапускает с очищенными переносами.
- **FreedomBox: зоны firewalld.** `internal` — это wlan0-точка, а LAN-порт
  (`eth0`) числится в `external`. Порт службы открывается правилом-источником
  в `external`, иначе снаружи тайм-аут при `policy accept` в iptables.
- **PocketBase-хуки знают только свои поля.** И `sanitize` (запись), и
  `viewFor` (ответ GET) собирают объекты поля-за-полем: новое поле
  каталога молча отбрасывается на обоих концах. Добавление поля — правка
  обоих хуков + перезапуск pocketbase; старые клиенты поля игнорируют.
- **Админская запись заменяет каталог целиком.** Правка/добавление/удаление
  шлют PUT со всем каталогом — база для списка всегда **свежий** GET
  с сервера (service/ops.py). Пустой или устаревший список унёс бы чужие
  записи в корзину: так 16.10.2026 страница потеряла каталог за одну
  правку.
- **FreedomBox: `sudo -u` сбрасывает окружение.** Для запуска от
  служебного пользователя с секретами — root читает `/etc/ai-bridge.env`
  и передаёт через `runuser -u ai-bridge -- env ...`.
- **PocketBase-хуки** в старом проекте изолированы и не видят верхнюю область
  файла; ошибки хуков пишутся в `pb_data/auxiliary.db`, а не в журнал.

Фоновая автопроверка (`--check-interval`, внутри `--serve`) проверяет
включённых по расписанию и сама отчитывается в статистику сообщества;
ключи на устройстве зашифрованы: `master.key` рядом с `keys.json`
(на Windows — привязан к учётной записи через DPAPI). Потеря
`master.key` — потеря ключей, ошибка об этом говорит прямо.

Проверено на живом сервере: вход (включая суперпользо­вателя через
`_superusers`), каталог (29 провайдеров), список моделей локального Ollama
(11 моделей), поток загрузки модели (`pulling manifest` → слои с процентами →
`success`), полная загрузка `qwen3:0.6b` через `--pull`, переключатели
`--enable/--disable` (для суперпользо­вателя — локально, флаг переживает
перезапуск). Счётчик статистики показывается колонкой в каталоге; `--check`
отправляет отчёт и показывает свежий счётчик сообщества.

Локальный сервис (`--serve`) проверен вживую: `/v1/models` отдаёт модели
включённых; чат через `ollama/qwen3:0.6b` дошёл до Ollama и вернул ответ
(шлюз подставляет чистое имя модели); SSE-поток идёт кусками до `[DONE]`;
оборвавшийся клиент — одна строка в журнале вместо traceback.

`--add`/`--remove` проверены вживую (вход суперпользо­вателем): запись с
явным id и запись с автослагом из русского имени («Мой LMS» → `moy-lms`)
попала в каталог, дубль id отклонён, удаление вернуло каталог к 29
записям (в корзине, восстановимо).

Страница (`--serve`) проверена вживую: каталог с пометками и статистикой
отдаётся на `/`, тумблер переключает флаг через полный путь (POST →
ops → снапшот), ключ принимается и остаётся на устройстве. Формы без
JavaScript; чужие Host (DNS-rebinding) и Origin (страница-обманка)
отклоняются. Форма правки (`/edit/<id>`) — определение (название, адрес,
модель, приоритет, где взять ключ) плюс **API-ключ и кнопку «показать
модели»**: ключ вводится здесь и остаётся на устройстве, список моделей
приходит прямо в форму, введённое не теряется. Справка о модели
(контекст/цена/способности) из правки убрана — она правится при
добавлении. Пустое поле значения не стирает — **кроме поля «Модель»**:
очищенное поле её убирает, иначе смена модели не состоялась бы никогда.

`--set-model`/`--edit` проверены вживую на FreedomBox: модель Ollama
сменена на `qwen3:0.6b` (видна в `/v1/models` без префикса, чат без
названия модели уходит в неё), справка (context/pricing/capabilities)
заполнена и видна в строке каталога. Попутно найдено: серверные хуки
`sanitize` и `viewFor` знают только свои поля — новые поля каталога
пришлось добавить в оба (бэкапы `.bak-pricing`/`.bak-viewfor` рядом).

Токен и объединённые модели проверены вживую: `--token` печатает токен
из `~/.ai-bridge/token`; `/v1/models` без токена → 401 с подсказкой, с
токеном → 14 моделей (настроенная `llama3.2` без префикса + 13 живых
моделей Ollama с префиксом `ollama/…`); чат через шлюз с токеном → 200,
модель подставлена чисто. 401 провайдера уходит в фолбэк.

Доступ извне проверен вживую (`--host 0.0.0.0`): страница по LAN-адресу
отдаёт форму входа (токен обязателен на не-loopback), API без токена →
401. `--page-auth` закрывает страницу и за туннелем до loopback. README
описывает три пути: Tailscale (рекомендован), Cloudflare Tunnel,
проброс порта (только с HTTPS).

новый аккаунт (креды в `/etc/ai-bridge.env` и в `config.toml` на ПК).
Старый инстанс (`app.devhorizon.online`, `127.0.0.1:8090`) остался
прежнему проекту. **Инцидент при миграции:** страница передавала
админские PUT с пустым списком каталога — 29 записей уехали в корзину
(восстановлены script'ом из `trash.json`); фикс и регрессия — коммит
«админские действия строят PUT по свежему серверному каталогу».

**Аккаунты и личные пространства (этап 1 мультипользовательской
версии).** Страница требует входа со всех адресов: логин/пароль
аккаунта сервера каталога, регистрация **открыта** (защита — модерация
админа на `/users`), аварийный вход — токен устройства (он же личный
`/v1`-токен админа, OpenWebUI не заметил изменений). Личное пространство:
у хозяина (суперпользо­вателя) ключи и переключатели живут в корне
устройства, у остальных — в `users/<id>/`; ключи шифруются общим
мастер-ключом. Человеку доступно: свой ключ, выбор своей модели,
тест-чат и свои `/v1`-токены (создать/отозвать на `/tokens`). Гейтвей
персональный: токен человека → его переключатели и его ключи. Админ
дополнительно: правки каталога, добавление/удаление, список людей с
удалением (аккаунт на сервере + личное пространство + токены + сессии).
`--page-auth` больше не нужен: вход обязателен всегда.

**Проверка живёт в кнопке «тест».** Отдельная кнопка «проверить»
(старый `GET /check/` — список моделей + отчёт) убрана из страниц:
главная проверка провайдера — настоящий ответ модели, и она же
засчитывается. После ответа тест-чата уходит отчёт в статистику
сообщества **под именем человека** (`ops.report_chat`,
`service/ops.py`); отчёт уходит и при отказе провайдера (это честная
неудача), но **не** при «нужен ключ» / «не выбрана модель» — это
состояние приставки, а не поломка модели, и солгать статистику нельзя.
Пустой список моделей при выборе модели (`GET /pick/`) успехом не
считается (`ops.report_models`).

Страница теста живая: **форма «Свой промпт»** (свой вопрос модели вместо
крошечного вопроса по умолчанию, плюс поле **картинки к вопросу** — для
vision-моделей и агентов-генераторов вроде 3D-для-Blender: «картинка →
ссылку»), ответ рендерится **markdown** (`core/markdown.py`, `![alt](url)`
становится картинкой) — так видны и медиа-ответы, и ссылки на файлы.
Секции генерации — **только** если каталог провайдера заявил модели
такого типа (`media_models`, один
поход в метаданные, не у всех подряд): **«Картинка»** (`generate_image`,
`/imgtest/<id>`; ссылка — `<img>`, base64 — data-URI разово), **«Озвучка»**
(`generate_audio` — `GET /audio/{text}`, плеер по ссылке из `Link`),
**«3D-модель»** (`generate_3d` — картинка-обязательна и только http(s),
результат — «скачать .glb»), **«Вектор»** (`embed_text` — длина и первые
числа) и **«Распознавание звука»** (`generate_transcript` — multipart
`/v1/audio/transcriptions`: свой аудиофайл, пусто — тестовый тон, текст в
поле результата), **«Музыка»** (те же `GET /audio/{text}`, но модели
выбираются по именам — их эндпоинты неотличимы от TTS), **«Обработка
звука»** (`process_audio`: смена голоса / очистка от шума / разделение
дорожек по своим эндпоинтам, в форме — «действие|модель») и подсказки
голосов из `/audio/models` (свободный ввод остаётся). Озвучка и 3D идут
**заданием jobs** (`Prefer: respond-async` → 202 → опрос `/v1/jobs/{id}`):
долгие генерации не удерживают соединение, провайдер без jobs отвечает
обычно — путь не меняется. В журнал ничего из этого не пишется — только
событие об итоге.

**Модель — личный выбор.** Выбранная человеком модель помечается флагом
`picked` в его снапшоте и **переживает обновление каталога**: серверная
модель не затирает чужой выбор (слить его может только сам человек,
выбрав другую). Админ меняет модель «по умолчанию» в каталоге, но не
отбирает личный выбор у людей. **Смена модели в правке (и админская
смена через --set-model) автоматически очищает справку** — «Способности»,
«Цену» и «Контекст»: они описывали старую модель, и пометка вроде
«vision» не должна солгать новой; в ответе — «справка о модели очищена».

**Добавление провайдеров — всем.** Форма `/add` полная: название, адрес,
ключ, кнопка «показать модели» (список у провайдера; если без ключа не
отдаёт — подсказка «введите API-ключ и нажмите ещё раз»), справка о
выбранной модели (context/pricing/capabilities — вручную, эти поля
видят все), логотипы (URL по строке) и страница с описанием и ценами
(поле `infoUrl`, оно же в каталоге v3). Админ кладёт в каталог для всех;
человек — в личное пространство (сервер не трогается вовсе). Логотип
(первая ссылка) и «описание и цены» показываются в строке каталога.

**GitHub Copilot — вход через OAuth** (`providers/copilot.py`; кнопка
«Войти через GitHub» на страницах ключа и правки): device-flow —
приставка показывает одноразовый код, человек вводит его на
`github.com/login/device`, и полученный токен `gho_` ложится в хранилище
как обычный ключ. Перед запросами сырой токен обменивается на токен
Copilot API (`api.github.com/copilot_internal/v2/token`, кэш до
истечения), заголовки — как у VS Code. **Каталог `/models` у Copilot
шире тарифа**: на бесплатном (sku с префиксом `free`) API принимает
только utility-семейства — список режется по `capabilities.family` и
поддержке `/chat/completions`, иначе любая «премиальная» модель отвечает
одинаковым 400 `model_not_supported`. Отказы 400/429 в тест-чате
переводятся человеческой причиной: какие модели доступны на тарифе и
когда повторить (минуты из заголовка `retry-after`).

**Реестр доступа.** Перед каждым запросом `/v1` приставка сверяется с
сервером каталога: человек **зарегистрирован и не заблокирован**? Проверка
онлайн, ответ помнится 5 минут на человека (десятки запросов = один
поход к реестру); недоступность реестра — пауза 60 секунд без повторов,
потом честный отказ «доступ не подтверждён». Блокировка — обратимая
(кнопки на странице «Пользователи», поле `blocked` в аккаунтах, при
первом старте приставка создаёт поле само); удаление остаётся крайней
мерой. Адреса провайдеров (URL) на страницах не показываются **никому** —
ни человеку, ни админу: витрина делится названием, адрес живёт только в
формах админа «добавить/править». Аксиома: **ключи не покидают устройство
человека** — приставки живут у людей; сервер — только каталог, реестр и
статистика.

**Маршрутизация помнит требование запроса.** Если запрос несёт картинки
(`image_url`) — переключение идёт только по vision-моделям; если инструменты
(`tools`/`tool_choice`) — только по моделям с `tools` в поле «Способности»
(поле текстовое, качество зависит от заполнения). Модель без имени, но с
требованием, сразу строит цепочку из подходящих. Ответ 400 с понятным
отказом («image_url is not supported», «does not support tools», а также
«модель работает только через WebSocket» — live-модели Gemini) — тоже
повод переключиться, а не отдать клиенту; прочие ошибки клиента (4xx)
идут как есть.

**Названная модель — не приговор.** Цепочка попыток: сначала провайдеры,
у которых модель настроена, затем — **последний шанс** остальными
включёнными по приоритету (`route()` в `core/routes.py`): пустой ответ
хуже чужего. Подмена не тайна — заголовки `x-ai-bridge-provider/model`
и журнал честно говорят, кто и чем ответил; в статистике запрос
записывается фактической модели. Префикс «провайдер/модель»
(«ollama/qwen3») решает только порядок — закреплённый идёт первым, но
его отказ переводит дальше. Переключение происходит на 401/402/403/404,
429, 5xx (404 — обычно «модель неизвестна этому провайдеру», смена
безвредна); 400/413/422 — вина клиента, идут как есть.

**Холодные локальные модели.** У локальных провайдеров (адрес — localhost,
приватный диапазон IP, `*.local`) первый запрос может ждать, пока модель
загрузится в память, — до пяти минут. Таймаут чата для таких провайдеров
автоматически поднят до 600 секунд (`is_local_url`/`_chat_timeout` в
гейтвее); у интернет-провайдеров остаётся настроенный. Списки моделей
(`/models`) этого не касаются — они отвечают сразу.

**Журнал событий** (`service/eventlog.py`, страница `/logs` — только
админ, обновление раз в 10 секунд): кто заходил, что нажимал, каждый
/v1-запрос с итогом — попытки, провайдеры, статусы, длительности,
причины отказов; события переживают перезапуск (файл
`~/.ai-bridge/events.jsonl` с ротацией по размеру). Просмотр самого
журнала не записывается — как и страница ожидания входа OAuth (её
автоопрос раз в 5 секунд засорял бы журнал). **Тела запросов и ответов
пишутся всегда** (решение хозяина: журнал видит только администратор,
страница закрыта посторонним — переписка не утекает; переключателя и
файла состояния больше нет), а base64-вставки (картинки в телах)
вырезаются с пометкой о размере — журнал не раздувается. Показываются
тела сворачивающимися блоками
(`<details>` — работают без JavaScript); автообновление страницы журнала
раз в 10 секунд **не перезагружает страницу, пока открыто хоть одно
тело**. Раскрытые тела восстанавливаются после обновления по уникальному
ключу события (`id`), а не по позиции — новые события сверху не ломают
восстановление. **Ежедневные
автосохранения** (`service/archive.py`): раз в сутки (и при старте
службы) снимки `events.jsonl` и `usage.json` кладутся в
`~/.ai-bridge/archive/ГГГГ-ММ-ДД-файл` — история растёт по дням,
ротация по размеру её не заменяет; сохранённый день не перезаписывается.

**Статистика** (`storage/usage.py`, страница `/stats` — доступна всем
вошедшим, обновление раз в 30 секунд): таблица **по моделям**, а не по
провайдерам в кучу. Каждому — его собственные расходы: сколько запросов
(и сколько из них переключились на другую модель — «дошли до fallback»),
сколько токенов вошло/вышло. Токены берутся из поля `usage` в ответе
провайдера: в обычном JSON — точно; в потоке SSE — поиск построчно по
ходу (`_absorb_usage`), если шлюз его не прислал — запросы считаются,
токены честно нулятся, не выдумываются. Попытка, отказавшая до тела
ответа, токенов не оставляет; итоговая неудача пишется как «✗».
Счётчики сообщества («сколько человек смогли») и способности
(`vision`/`tools`) берутся из каталога. **Чужие расходы не показываются** —
у админа сверху колонка «все люди» с суммами. Данные — агрегаты в
`~/.ai-bridge/usage.json` (не секреты, только цифры; ротация по размеру
как у журнала), переживают перезапуск. Пишет их гейтвей в момент ответа
чата (`_record_usage`); ключ — «провайдер/модель», поэтому личный выбор
модели попадает в свою строку.

**Три списка моделей** (`storage/lists.py`): приставка сама ведёт
три списка, рук не нужно. Белый — **четыре файла по группам**
способностей: `whitelist-text.txt` (только текст), `whitelist-vision.txt`
(видят картинки), `whitelist-tools.txt` (вызывают инструменты),
`whitelist-vision-tools.txt` (и то и другое). Группа — подпись модели,
источник правды — `capabilities.json` плюс рукописная справка; успех
кладёт модель в файл её группы и **перекладывает**, когда она доказала
новую способность. Сортировка внутри уровня по `_fit` в `core/routes.py`:
текстовый запрос идёт к дешёвой текстовой группе первой, картинка — к
vision, инструменты — к tools; текст никогда не достаётся vision-модели.
`blacklist.txt` — после жёсткого отказа (404/5xx/таймаут/«только
WebSocket»/мусор); «почти» навсегда: если больше некому служить —
приставка берёт и чёрный, лучше чужой ответ. `greylist.txt` —
**персональный** (`users/<id>/greylist.txt`, у хозяина — в корне): мягкий
отказ (402/429 или спрятанное «мало кредитов / попробуй позже» в 200)
отстраняет модель на сутки; через сутки она просыпается и идёт после
неизвестных («пытается быть белой»): успех — в белый (в свою группу),
снова мягкий отказ — спит ещё сутки, **три цикла подряд — в чёрный**.
Уровни цепочки: белый(1) → неизвестный(2) → проснувшийся серый(3) →
чёрный(4); сортирует `enabled()` в `core/routes.py` по `_tier` и `_fit`.
Старый плоский `whitelist.txt` мигрируется при старте по группам
(оригинал — `whitelist.txt.migrated`). Вина клиента (400/413/422) и
отказ «не поддерживает картинки/инструменты» списки не трогают. После
**каждого** запроса в журнале событие `решение` (со статусом и телом):
«подтвердила себя — в белом (группа …)», «переложена: text → vision»,
«серый до <времени>», «в чёрном списке», «вина клиента — списки не
тронуты». Содержимое файлов админ видит на странице статистики (белый —
четырьмя секциями); файлы перечитаются на каждый запрос — правка
вступает в силу без перезапуска.

**Живое состояние локальных** (`providers/client.py` →
`Provider.local_status`): строка каталога для включённых локальных
показывает, что в памяти прямо сейчас, — Ollama `GET /api/ps`
(модели + доля VRAM), LM Studio `/api/v0/loaded`/`/api/v0/health`.
Таймаут 1.5 с (висящий сервер не держит страницу), недоступен — молча
без строки.

**Репутация моделей** (`storage/reputation.py`, файл `reputation.json`):
приставка сама помнит, кто отвечает плохо, — человеку не надо следить.
Штраф начисляется за честно распознанные поломки: отказ «умеет только
через WebSocket» / «не поддерживает картинки/инструменты», HTTP 404
(модель неизвестна провайдеру), спрятанная ошибка в ответе 200 и мусор
вместо JSON, хотя шлюз обещал JSON (`_garbage_answer`). **Ошибка клиента
(прочие 4xx) штрафом не считается** — иначе кривой запрос приложения
забанил бы все модели. Три поломки за 15 минут → пауза 30 минут, каждая
следующая пауза удваивается (с потолком в сутки). **Нормальный ответ
обнуляет штрафы модели немедленно** — модель сама себя реабилитует.
Цепочка попыток пропускает модели на паузе, **но если свободных не
осталось — берёт и наказанные**: чужой ответ лучше мёртвой ошибки, а
удачный запрос снимет паузу. Пауза — не бан, это предпочтение.
Админ видит секцию «На паузе» на странице статистики (кто, сколько
штрафов, когда вернётся) с кнопкой «вернуть» (`POST /stats/release`) —
для ложных срабатываний; в журнале каждая пауза — событие с причиной.

**Способности учатся сами** (`storage/capabilities.py`, файл
`capabilities.json`): заполнять поле «Способности» руками необязательно —
приставка учится на практике. Запрос с картинкой дошёл до ответа →
модель умеет `vision`; запрос с инструментами → `tools`. Честный отказ
провайдера («does not support tools», «image_url is not supported» — те же
подсказки, что переключают провайдера) доказывает обратное. Кто последний,
тот и прав: **выученный факт перекрывает рукописную справку в обе
стороны** — успех дописывает способность, отказ вычёркивает; позже успех
переворачивает выученный запрет. Подсказка «только через WebSocket» — не
про способности, её не учим (но событие в журнале отмечаем). Знание живёт
в том же ключе «провайдер/модель», что и репутация, и вливается в
маршрутизацию через текст поля «Способности» (`_taught_entries`/
`_merge_capabilities` в гейтвее) — `core/routes.py` не меняется. Кнопка
«вернуть» на паузе репутации способности не трогает. **Каждый шаг
обучения — событие в журнале** (тип `способности`): «выучила vision»,
«подтвердила vision», «перевернула „не умеет“», «отозвала vision»,
«выучила „не умеет tools“» — с цитатой причины-отказа. Когда цепочка
пуста из-за способностей, ошибка клиенту и журнал честно говорят:
«пропущено N моделей: запрос требует vision» (`_skipped_by_capability`)
— почему фолбэк «пустой», видно сразу.

## 11. Правила разработки

1. **Чистое ядро.** В `core/` — только функции «данные → данные». Ни сети,
   ни файлов, ни времени. Всё, что снаружи, — в `providers/` и `storage/`.
2. **Тест на стадии отладки.** Нашёл баг — сначала пишешь воспроизводящий
   тест на реальных данных из логов, потом чинишь. Тест остаётся как регрессия.
3. **Быстрая проверка.** `uv run pytest` — офлайн, ≈530 тестов, ~20 с.
   Тесты по одному файлу: `uv run pytest tests/test_catalogue.py`.
4. **UI в конце.** Интерфейс добавляется, когда известен весь набор функций,
   а не после каждой мелочи.
5. **Секреты — только в окружении.** В репозиторий не попадают ни пароли,
   ни ключи (`config.toml` в `.gitignore`).

## 12. Команды

```bash
uv sync                     # поставить зависимости
uv run pytest               # прогнать все тесты
uv run python app.py        # каталог с сервера и статистика
uv run python app.py --models ollama
uv run python app.py --check ollama   # проверка + отчёт статистики
uv run python app.py --pull ollama    # скачать модель (Ctrl+C — отмена)
uv run python app.py --enable ollama  # включить (локально; обычный — и на сервер)
uv run python app.py --disable ollama # выключить
uv run python app.py --add "Мой LMS" http://127.0.0.1:1234/v1 qwen3-8b
uv run python app.py --remove moy-lms # убрать: админу — в корзину, человеку — своё
uv run python app.py --set-model ollama qwen3:0.6b  # модель по умолчанию
uv run python app.py --edit ollama context=128K pricing='$0.1/1M' capabilities='vision, tools'
uv run python app.py --serve          # служба: API на :8080/v1 + страница на :8080/
uv run python app.py --token          # токен приставки (для /v1/* и страницы на LAN)
uv run python app.py --serve --host 0.0.0.0 --page-auth  # доступ из LAN/Tailscale
uv run python app.py --serve --check-interval 0  # без фоновой автопроверки
```

Логин: переменные `AI_BRIDGE_EMAIL` и `AI_BRIDGE_PASSWORD`
(или поля `email`/`password` в `config.toml`, который в репозиторий не идёт).
